# Render Staging migration — Ayansha Health Care

**Prepared:** 16 November 2026  
**Status:** Draft configuration only. No Render service/database has been created and no Railway data has been exported or copied.

## Scope and isolation

- This is a separate **Staging-only** Render Blueprint for the existing GitHub repository.
- It reuses the existing root Dockerfile and the current Staging branch, `staging/auth-abuse-protection-with-role-portal`.
- It creates one Render Postgres 18 database and one Docker web service in the Singapore region.
- The Render database is private-only (`ipAllowList: []`) and the web service receives its internal `DATABASE_URL` from the Render database resource.
- Auto-deploy is disabled. Later code changes do not silently deploy; an operator must trigger a reviewed deploy.
- The Blueprint starts with an empty database. It does **not** export, copy, restore, seed, or delete any Railway records.
- The existing Railway Staging and Production services/volumes remain separate and untouched.

Current Render pricing shows:

**Estimated Staging baseline: about $13/month**, using a 1 GB Postgres disk, before extra storage above the included amount, bandwidth, tax, and any other usage. The paid web service is required because the Blueprint uses a pre-deploy migration command. Review the live Render billing page before approving Blueprint sync.

The small Postgres plan has 256 MB RAM and is intended only for a low-volume Staging environment. Reassess using real usage metrics before increasing capacity.

## Data protection gate

The low-cost Hobby configuration is **not a healthcare compliance certification**. Render lists HIPAA-enabled workspaces under its Scale plan ($499/month flat, compute additional), but Render's current HIPAA documentation says Singapore region is not supported for HIPAA-enabled workspaces. Therefore this proposed Singapore Staging service is strictly for synthetic/anonymized QA data and must not process or store identifiable patient, family, insurance, prescription or other clinical data. Any future PHI/clinical-data hosting needs a separate approved region/workspace and privacy, contractual, security, residency and regulatory review.

Do not restore a Railway database backup into Render merely because the database is Staging. First classify its contents, verify the backup, and confirm that the export is approved for the destination. Production database URLs, secrets and records must never be used here.

## Service configuration

- Dockerfile: `./Dockerfile` at repository root.
- Health check: `GET /health`.
- Database version: PostgreSQL 18, 1 GB disk size (the minimum allowed Blueprint disk size for a new database).
- Runtime: `NODE_ENV=production`; Render supplies `PORT`.
- `JWT_SECRET` is generated by Render.
- `ADMIN_EMAIL` and `ADMIN_PASSWORD` are requested as dashboard-only secret inputs (`sync: false`). Do not put their values in GitHub, chat, or YAML.
- No OTP, MSG91, Razorpay, WhatsApp, AI, insurance object-storage, or malware-scanner secrets are configured. Patient/Doctor OTP and other provider-dependent features must remain fail-closed/not ready until their providers are separately approved and securely configured.
- Same-origin web pages can use the API. If an external browser frontend is later connected, add only its exact HTTPS origin to `CORS_ALLOWED_ORIGINS` through Render's secret/environment settings; do not use a wildcard.

## Database preparation command

The Blueprint runs `node scripts/render-predeploy.js` before each deploy. The script:
1. Requires the Render-provided `DATABASE_URL`.
2. Acquires a PostgreSQL advisory lock to prevent overlapping schema preparation.
3. Applies the existing base `db/schema.sql`.
4. Replays the existing sorted `db/migrations/*.sql` set.
5. Logs migration filenames only; it never prints connection strings or driver details.

The current seven migration files were statically reviewed on the existing Staging branch. That is not a substitute for a verified backup, a restore rehearsal, or a schema-state check. Re-review every new migration before merging or deployment.
